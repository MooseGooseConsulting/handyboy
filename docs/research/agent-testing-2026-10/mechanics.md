# Mechanics of driving and observing an MV3 extension under test

Date of research: 2026-10-11. Sources read via `gh api` and Exa fetch; nothing cloned, no browser tool used. Everything read is treated as data. Items marked INFERENCE are mine, not stated by a source.

## 0. Facts about this repo that frame the findings (read locally)

- `wxt.config.ts` pins the extension ID with a manifest `key`, sets `webExt.disabled: true` (never launch a browser), and requests `tabs`, `scripting`, `storage`, `nativeMessaging`, `debugger`, `downloads`. It does NOT request `tabGroups`.
- `src/host/native.ts` already has a `NativePortApi` seam over `chrome.runtime.connectNative`, with message types `runlog.append` / `log.append` and acks. So a telemetry channel (extension -> native host -> file) already exists. The seam has a fake for tests (`FakeNativePort`).
- `entrypoints/background.ts` already persists state "across SW restart in chrome.storage.session" (line ~81).

## 1. Loading and driving an extension in e2e (the standard patterns)

### 1.1 Playwright: `launchPersistentContext` + `--load-extension`
- Official docs (microsoft/playwright `docs/src/chrome-extensions-js-python.md`, rendered at playwright.dev/docs/chrome-extensions): extensions only work in Chromium with a persistent context; args `--disable-extensions-except=<path>` and `--load-extension=<path>`; MV3 service worker obtained with `context.serviceWorkers()[0] ?? await context.waitForEvent('serviceworker')`; `extensionId = serviceWorker.url().split('/')[2]`; fixture passes `''` as userDataDir (= fresh temp dir per context) and does `await context.close()` after `use`. "Google Chrome and Microsoft Edge removed the command-line flags needed to side-load extensions, so use Chromium that comes bundled with Playwright."
- Playwright's own tests (microsoft/playwright `tests/library/chromium/extensions.spec.ts`): `it.skip(({channel}) => channel?.startsWith('chrome'), '--load-extension is not supported in Chrome anymore')`; tests the service worker via `sw.evaluate(...)`, `context.waitForEvent('request'|'response')` for SW fetches, and SW stop/restart via CDP `ServiceWorker.stopWorker/startWorker` (Playwright keeps the same Worker object across the restart).
- MetaMask, real production harness (MetaMask/metamask-extension `test/e2e/playwright/shared/chrome-extension-harness.ts`):
  - `userDataDir = await mkdtemp(path.join(os.tmpdir(), 'mm-chrome-e2e-'))` per launch; `cleanup()` does `context.close()` then `rm(userDataDir, {recursive, force})`. This is their state isolation: one throwaway profile per test run.
  - args include `--no-first-run`, `--no-default-browser-check`, `--disable-component-update`, and `--proxy-server=http://127.0.0.1:8000` (so MV3 SW traffic goes through a mock server; Playwright's page-level `proxy:` option does not cover SWs, and `ignoreHTTPSErrors` does not cover SWs, hence `--ignore-certificate-errors`).
  - Headless gotcha spelled out in a comment: Playwright `headless: true` selects `chromium-headless-shell`, which does NOT support extensions; they pass `headless:false` and add `--headless=new` themselves.
  - Extension ID is computed deterministically from the manifest `key` (sha256 of the base64-decoded key, first 32 hex chars mapped 0-9a-f -> a-p), with SW-URL discovery and page-URL scanning as fallbacks. It still waits for the SW first, because "the URL isn't serviceable until the worker registers -- surfacing as `net::ERR_ABORTED`".
  - Downloads: `acceptDownloads: true, downloadsPath: <repo>/test-artifacts/downloads`.
  - nanobrowser-v2 already has a pinned `key`, so the same derivation works here.
- ankit/stylebot `e2e/fixtures.ts`: `fs.mkdtempSync(path.join(os.tmpdir(), 'stylebot-e2e-'))` per worker, a worker-scoped `BrowserPool` reusing one browser+extension per worker, relaunching on demand if Chrome died; wait for the `onInstalled` welcome tab with a 15 s timeout; separate 60 s launch budget; `extension.evaluate(() => chrome.storage.local.clear())` between tests.

### 1.2 Puppeteer
- pptr.dev/guides/chrome-extensions: `puppeteer.launch({ enableExtensions: [pathToExtension] })`, or `enableExtensions: true` then `await browser.installExtension(path)` (returns id), `browser.extensions()`, `browser.uninstallExtension(id)`. SW via `browser.waitForTarget(t => t.type()==='service_worker' && t.url().endsWith('background.js'))` then `.worker()`. Popup via `worker.evaluate('chrome.action.openPopup()')`; `page.triggerExtensionAction(extension)`; content-script realms via `page.extensionRealms()`. Chromium-extensions list thread (PSA 1-g8EFx2BBY) says this "works across all Chrome channels".
- Programmatic unpacked-extension installation through CDP `Extensions.loadUnpacked` or WebDriver BiDi `webExtension.install` requires `--enable-unsafe-extension-debugging` and `--remote-debugging-pipe`, according to the [Chrome Extensions team's RFC reply](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/aEHdhDZ-V0E). This is a requirement of those install commands, not of CDP generally: CDP can connect over a remote-debugging port, and launch-time `--load-extension` is a separate mechanism (as in the BrowserSkill CI example in `ci-model.md` §4b). Do not conflate installing an extension with later controlling an already-loaded extension over CDP.

### 1.3 WebdriverIO / Selenium
- webdriver.io/docs/extension-testing/web-extensions: Chrome via `'goog:chromeOptions': { args: ['--load-extension=<dist>'] }`; mid-session `browser.installExtension(path)` / `uninstallExtension(id)` (v10, BiDi only). For Chromium BiDi install: `--enable-unsafe-extension-debugging --remote-debugging-pipe --user-data-dir=<dir>` ("Chrome 136 and newer also require `--user-data-dir` whenever `--remote-debugging-pipe` is set"). Popups are tested by navigating to `chrome-extension://<id>/popup.html`; toolbar-click is not automatable.
- webdriverio issue #14839: `--disable-features=DisableLoadExtensionCommandLineSwitch` stopped working at Chrome 142; BiDi install is "essential" after that.

### 1.4 Chrome's own harness
- chromium.googlesource.com `extensions/docs/extension_tests.md`: `ExtensionApiTest` loads a test extension whose `background.js` calls `chrome.test.runTests([...])`, with `chrome.test.succeed()/assertNoLastError()`; `BackgroundScriptExecutor` runs JS in an extension's background context and returns via `chrome.test.sendScriptResult`; `ExtensionBrowserTest` maps `chrome-extension://<id>/_test_resources/...`. These are in-process C++ browser tests; not usable from outside against branded Chrome. The takeaway is the shape: a result channel from inside the extension (`sendScriptResult`) rather than DOM scraping.

### 1.5 `--load-extension` status (critical for the "real Chrome" question)
- Chrome 137 removed `--load-extension` from branded Chrome (PSA groups.google.com/a/chromium.org/g/chromium-extensions/c/1-g8EFx2BBY). Remains in Chromium and Chrome for Testing. Chromium commit 04f6233ce5be (chromium/src) hard-codes the block `#if BUILDFLAG(GOOGLE_CHROME_BRANDING) && !BUILDFLAG(IS_CHROMEOS)`, deleting the old `kDisableLoadExtensionCommandLineSwitch` feature, which is why the `--disable-features=...` workaround died (Chrome 142 per SO 79657438 and webdriverio #14839).
- `--disable-extensions-except` also being removed (Chrome 139 follow-on thread, referenced in the RFC thread).
- Consequence: a Playwright/Puppeteer rig must use Chromium / Chrome for Testing (Playwright `channel: 'chromium'`), or the BiDi/CDP pipe install. The user's real Chrome already has the extension installed via "Load unpacked", so a cloned profile of it keeps the extension without any flag (INFERENCE: the unpacked path lives in the profile's Preferences; not verified, needs an experiment; Secure Preferences HMAC might reject a moved file).

## 2. Attaching to a normal, running Chrome (Chrome 136 and 144 rules)

- Chrome 136+: `--remote-debugging-port` and `--remote-debugging-pipe` "will no longer be respected if attempting to debug the default Chrome data directory" (developer.chrome.com/blog/remote-debugging-port). Code: chromium `chrome/browser/devtools/remote_debugging_server.cc` `IsRemoteDebuggingAllowed` returns `kDisabledByDefaultUserDataDir` when `kDevToolsDebuggingRestrictions` is on and the dir is the default. Playwright issue #35836 shows the symptom (`about:blank`, profile state missing) and a workaround `--disable-features=DevToolsDebuggingRestrictions` that a later commenter reports not working on Chrome 141.
- Chrome 144+: `chrome://inspect/#remote-debugging` toggle (chromium commit 27485803 "Add remote debugging toggle to chrome://inspect", prefs `kDevToolsRemoteDebuggingEnabled`, gated by `kDevToolsAcceptDebuggingConnections`). Per the Chrome blog (developer.chrome.com/blog/chrome-devtools-mcp-debug-your-browser-session, 2025-12-11): remote debugging is off by default; the user enables it on that page; each `--autoConnect` request from chrome-devtools-mcp triggers a per-connection permission dialog, and "while a debugging session is active, Chrome displays the 'Chrome is being controlled by automated test software' banner".
- Practical details from issue trackers (not Chrome docs, so lower confidence):
  - The toggle-enabled server is WebSocket-only; `/json/version` returns 404; clients must read `DevToolsActivePort` and build `ws://127.0.0.1:<port><path>` (vercel-labs/agent-browser #516, ChromeDevTools/chrome-devtools-mcp #772/#1194, trycua/cua #2916). One report says the port changed to 61545 in Chrome 146 (chrome-devtools-mcp #1194).
  - Clients time out while waiting for the user to click Allow (agent-browser #516; PR #1119 raised the timeout).
  - Playwright `connectOverCDP` could not attach to this mode as of 2026-04 (microsoft/playwright #40027); Puppeteer works via `handleDevToolsAsPage: true` (as cited in that issue).
- Who tests in the user's real profile: chrome-devtools-mcp `--autoConnect` (Google), agent-browser `--auto-connect`, trycua/cua `browser_prepare` (existing-profile route), and the Playwright MCP Bridge extension (section 3.3). All of them attach with CDP (consent dialog + automation banner) or `chrome.debugger` (yellow banner). None I found runs a test suite in the real profile without a debugger or consent step. The no-CDP alternatives are in sections 3 and 4.

## 3. How agent extensions own, group and close their tabs

### 3.1 The pattern (no debugger, MV3, plain extension APIs)
shibanyu333/agent-tab-bridge (`extension/background.js`, `extension/manifest.json`):
- Manifest permissions: `tabs, tabGroups, scripting, storage, alarms` (no `debugger`). README: "No `chrome.debugger`, so no 'started debugging this browser' banner, ever."
- `open_tab`: `chrome.tabs.create({ url, active: false, windowId })` where `windowId` is `chrome.windows.getLastFocused({windowTypes:['normal']})` or the window of the session's existing group; then `ownTab()`.
- `ownTab`: records `tabOwner: Map<tabId, sid>` and `s.tabIds: Set`, sets `chrome.tabs.update(tabId, {autoDiscardable:false})`, then `addToGroup`: first tab does `groupId = await chrome.tabs.group({tabIds:[tabId]})` then `chrome.tabGroups.update(groupId, {title, color})`; later tabs pass `groupId`. Grouping failure is swallowed ("grouping is a visual marker; failure must not fail the command").
- Persist/restore: `chrome.storage.session.set({atbState})`, and `restore()` re-validates each id with `chrome.tabs.get` after an SW restart.
- `chrome.tabs.onRemoved` removes the id from the owner maps.
- End of task: `session_end` does `chrome.tabs.remove(ids)` for owned tabs, excluding tabs the user's own page "adopted" (comment: "never close the user's own pages"), releasing adopted ones with `ungroup` only when the tool itself had grouped them.
- Screenshot caveat: `tabs.captureVisibleTab` only captures the active tab of a window, so it momentarily activates the tab, captures, and switches back, serialized by a global lock.

### 3.2 Other real implementations of the same idea
- limecloud/lime `extensions/lime-chrome/lib/cdp/tabs/agent-group.js`: `AgentGroupManager` with a promise queue so concurrent `addTab` calls do not each create a group; on reconnect, `chrome.tabGroups.query({title})` to recover the existing group; `dissolve(agentTabIds)` closes agent-created tabs with `chrome.tabs.remove` and only ungroups tabs not in that set.
- Skyvern-AI/skyvern `skyvern/browser_extension/extension/tab_scope.js`: group "Skyvern Controlled" (purple); persists `scopedTabIds`, `scopedTabGroupIds`, `createdTabIds`, and a `pendingTabCreation` marker (crash recovery for a tab created but not yet recorded); an alarm sweeps popup groups; a tab leaving the scope cancels its in-flight operations.
- can1357/oh-my-pi `packages/browser-relay/extension/background.ts`: `tabGroups.query({title, windowId})` to reuse a group, `enqueueGroupOp` serialization, `ungroup` and `tabs.remove` messages.
- jackwener/OpenCLI issue #1627 (closed "by design"): after ephemeral tabs close, the empty named group is kept as a reusable anchor; they verified the next lease re-adds into the same group id. Related titles: #1760 "Empty tab group residue causes resolveTab to reuse user's existing tabs instead of creating new automation window", #2097 "Multiple tab groups can accumulate". Lesson: group reuse is a source of bugs; a per-run group (or a window) avoids stale-anchor reuse. (Read only the titles/body shown by search, not the issues in full.)
- oil-oil/my-browser README: guidance that agents "track tabs opened for the current task and close temporary ... tabs before calling `detach`", and keep tabs holding unfinished uploads/logins/QR verification. leeguooooo/chrome-use: one colored tab group per `--session`, tabs open unfocused, and `Emulation.setFocusEmulationEnabled` so background tabs are not render-throttled (that last part is CDP).

### 3.3 Playwright MCP Bridge (the official Microsoft example of "attach to the user's own browser")
- microsoft/playwright `packages/extension/src/ui/connect.tsx`: relay URL must be loopback (`127.0.0.1` or `[::1]`), protocol version check, the user picks a tab to allow, or a stored token auto-connects; a 20 s keepalive message keeps the MV3 SW above its idle timeout while the user decides; copy: "You can drag tabs into the Playwright group later to make them accessible to the client".
- microsoft/playwright-mcp PR #1478: `createTab` calls `chrome.tabs.create()` then attaches the debugger; tracks `_playwrightTabIds`; per-`mcpRelayUrl` isolated connection state; detaches from all its tabs on close. It uses `chrome.debugger`, so the banner and detectability trade-off applies. The extension in this repo already declares `debugger`.

## 4. Resetting state between tests

Observed mechanisms, from heaviest to lightest:
1. Fresh user-data-dir per run: MetaMask harness (mkdtemp + rm), stylebot (mkdtemp per worker), Playwright docs (`''`). Cleanest; needs a launched browser we control, so not the user's running Chrome.
2. Cloned logged-in profile (for real sessions):
   - tolmachevmaxim/chrome-profile-session: copies only auth-relevant files (`Cookies`, `Login Data`, `Local Storage`, `Network/`) plus top-level `Local State` to a temp dir, launches real Chrome on the clone with `--user-data-dir` + `--remote-debugging-port`, and removes the clone on exit. Its description is macOS-focused. Cookies stay Chrome-encrypted and are decrypted by Chrome itself via the OS keystore.
   - teng-lin/rookie-cookies CI workflow: on Linux, a non-default user-data-dir works with libsecret/gnome-keyring ("Chrome Safe Storage" key is per OS user, not per directory), and notes "Chrome refuses CDP/remote-debugging when the user-data-dir is the default profile location". tsuna/chrome-macos-linux-migration documents the secret-tool schema `chrome_libsecret_os_crypt_password_v2` and that copying across OSes breaks encrypted data (not a concern same-machine). Delete `SingletonLock/Cookie/Socket` from a copied dir before launch (tsuna README; also in the SO 79920001 answer).
   - blockether/spel docs claim Chrome 136+ "intentionally broke all automation approaches that rely on Chrome's own cookie access from subprocesses" and decrypt cookies themselves. This conflicts with chrome-profile-session; I did not resolve it. It is a question for a local experiment, not a settled fact. App-Bound Encryption applies to Windows only (Chrome blog, March 2025).
3. In-extension reset via a test-only command channel (no debugger):
   - ramoncoroso/mirilla `lib/e2e-bridge.ts`: compile-time gated (`if (__E2E__)`, so not in the shipped build); a fixed set of ops (`clear`, `setStorage`, `getStorage`, `closeTab`, `tabIdByUrl`, `activate`, `openScan`, ...) executed in the background; commands arrive from an ordinary http page via a content script `e2e-relay` because geckodriver cannot touch `moz-extension://` tabs; "only predefined commands (the extension CSP forbids eval)".
   - proshunsuke/tab-position-options-fork `e2e/utils/helpers.ts` `clearExtensionStorage(serviceWorker)`: `serviceWorker.evaluate` clears `storage.sync`, `storage.local`, `storage.session`, resets module state via `globalThis.__testExports`, then restores defaults.
   - CapSoftware/Cap `apps/chrome-extension/e2e/*.spec.ts`: `chrome.storage.local.clear()` then seed `[authKey]: {authApiKey: 'auth-e2e', ...}` at the start of each spec.
   - MetaMask: `window.stateHooks` / `globalThis.stateHooks` (`app/scripts/lib/setup-initial-state-hooks.ts`, `ui/index.js`) expose `getCleanAppState`, `getPersistedState`, `getWebVitalsMetrics` "in test mode" only for the test driver to read. Also a fixture builder (`test/e2e/fixtures/fixture-builder-v2.ts`) to seed state.
4. INFERENCE for nanobrowser-v2: because the native host already talks to the SW, the host can carry such a test-only command (e.g. `test.reset {runId}`), accepted only when the build has an `E2E` flag, with a closed op set like mirilla's. That gives storage clear/seed and tab cleanup without CDP. Alternative that avoids destructive clears in the user's real profile: namespace keys per run (`runs/<runId>/...`) and delete only that namespace at the end. I found no project doing the namespacing variant; it is my suggestion.

## 5. Telemetry out of an extension

- Native messaging constraints (developer.chrome.com/docs/extensions/develop/concepts/native-messaging, GoogleChrome/developer.chrome.com site/en/docs/extensions/mv3/nativeMessaging/index.md): `connectNative` keeps the host alive until the port is destroyed, while `sendNativeMessage` starts a new host process per message; host to browser limit 1 MB per message; browser to host limit stated as 4 GB in one doc version and 64 MiB in another quote (guest271314/NativeMessagingHosts README, and the IberAI/native-messaging crate calls 64 MiB "Chrome's documented limit"); stdout is protocol-only, so debug output must go to stderr or a file; host errors go to Chrome's own log (start Chrome from a terminal to see them).
- MV3 SW lifetime with a native port: Chrome 100 notes claim a `connectNative` port keeps the SW alive; GoogleChrome/developer.chrome.com issue #2688 reports the SW still dying after 5-6 minutes in a specific `onConnectExternal` + `runtime.connect` combination. Not a general refutation, but a reason to persist run state (as in section 3.1) and to send a heartbeat. Playwright's extension keeps its SW alive with a 20 s `chrome.runtime.sendMessage({type:'keepalive'})` ping from a visible page (section 3.3).
- OpenTelemetry in an SW:
  - `@opentelemetry/exporter-trace-otlp-http` historically used XHR/sendBeacon and failed with `window is not defined` in workers (open-telemetry/opentelemetry-js #3168, fixed via #4157/#4438). A fetch transport now exists: `experimental/packages/otlp-exporter-base/src/transport/fetch-transport.ts` (keepalive capped at 9 concurrent requests and a body-size budget; uses `fetch.__original` to avoid span-on-export loops); PR #5807 "add fetch transport for fetch-only environments" merged; #6377 exports `createFetchTransport` and `createRetryingTransport` for custom use. I did not verify which released version first contains each; check the installed package.
  - Working examples that run `WebTracerProvider` in an extension background: redpanda/chrome-extension-example `src/background.ts` and pedrogranja/chrome-extensions-test `src/background.ts` (Grafana Faro FetchTransport to a local collector `http://localhost:8027/collect`). These are demos, not agent projects.
  - OpenTelemetry's own caveat (issue #4631, comment by david-luna): in a ServiceWorker, async context propagation across `await` is not handled by the default context managers, so parent/child links need explicit context passing. INFERENCE: for an agent loop in an SW, create spans with explicit parent contexts (or write span-shaped JSON lines yourself).
- Langfuse / LangSmith / Laminar: all are OTel-based (Langfuse JS `@langfuse/otel` `LangfuseSpanProcessor` is documented for Node.js >= 20; `@langfuse/browser` is "browser-safe client for public-key score ingestion", i.e. not the tracing exporter). I found no open-source agent extension that exports traces directly to them from the SW, and the secret keys would have to live in the extension, which this repo forbids for the API key ("The extension never holds the API key. The native host attaches it."). So the fit here is: extension emits span-like events over the existing native port, host (Node) owns the exporter and credentials. Langfuse accepts raw OTLP at its endpoint (langfuse.com/docs/sdk/overview: "send OpenTelemetry spans to the Langfuse OTel endpoint"), and Laminar can run self-hosted (laminar.sh docs show a local `base_url`). INFERENCE, not seen in a project.
- Test-side observation without CDP: MetaMask exposes `stateHooks.getWebVitalsMetrics()` "in test mode"; the mirilla bridge exposes `history`/`getStorage`; Chrome's own tests use `chrome.test.sendScriptResult`. The common shape is a closed set of read ops behind a build flag, returning plain JSON.

## 6. Gaps and unresolved questions (write down, do not decide)

1. Does a cloned user-data-dir of the user's real profile keep the unpacked extension and its logins on Linux (Secure Preferences HMAC, keyring key, `Singleton*` locks)? Needs a local experiment (read-only copy, no site automation).
2. With the clone launched by a branded Chrome: `--load-extension` is ignored, so we rely on the extension already being in the cloned profile; if that fails, Chrome for Testing + `--load-extension` gives a fresh but logged-out profile.
3. Can a clone be driven without any debugger at all? The no-CDP drive would be the extension's own test command channel over the native host (section 4.3/4); then we only need to launch a process (`google-chrome --user-data-dir=<clone> <url>`), never attach. I did not find a project that does the launch-plus-command-channel combination end to end; mirilla is the closest.
4. Does a window per run (`chrome.windows.create`) beat a tab group for isolation from the user's own tabs? Agent-tab-bridge and Skyvern chose groups in the user's window; OpenCLI issues suggest a dedicated automation window avoids reusing user tabs. No head-to-head evidence.
5. The 4 GB vs 64 MiB browser-to-host limit discrepancy: check Chromium source (`chrome/browser/extensions/api/messaging/native_message_*`) before relying on large trace payloads; keep each message well under 1 MB anyway because of the host-to-browser cap (acks are small).
